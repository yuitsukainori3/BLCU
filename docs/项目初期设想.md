# 安全帽智检 · 初期设想

> v0.1 ｜ 2026-11-02 ｜ 内部讨论稿，非正式
>
> 这份文档只干一件事：把立项初期我们对"做什么、为什么这么做、最后长什么样"的想法记下来，方便组内对齐，也方便以后往正式文档里搬。它不是申报书，不追求写全；细节以 `docs/` 下的专门文档为准。
>
> 数字口径：凡标"实测"的都注明评测集和出处，没测的写"待实测"。应用层 `backend/`、`frontend/` 目前只有占位 README，一行代码都还没有——第 3 节写的是打算怎么做，不是已经做成。

## 1 一句话

用工地已有的摄像头，接两个 YOLO11 模型和一个网页，把"谁没戴安全帽"变成一条带截图、能查到、能统计的记录。

拆开是三件事：

| 要解决的问题 | 靠什么 | 真正的难点 |
|---|---|---|
| 这颗头戴没戴 | 自训两类模型（head / helmet） | 安全帽和裸头框的是同一颗头，差别只在头顶那点像素 |
| 这颗头是谁的 | COCO 预训练的 person 检测 + 几何归属规则 | 人多、遮挡时会挂错人 |
| 管理层怎么看 | 能连摄像头、能看实时画面和告警的网页 | 视频进浏览器这一步比模型更容易翻车 |

三项里，第二项是"人-头盔匹配"要解决的事，也是这个项目跟"跑个 YOLO 演示"的区别所在。

## 2 项目目标

### 2.1 交付三样东西

1. **一个两类检测权重**（head / helmet），附一张说清"在哪测、测了多少"的指标表；
2. **一套判定逻辑**：把头框挂到人身上，按连续帧出结论，落成事件（时间、摄像头、截图、状态）；
3. **一个 Web 管理终端**：连摄像头看实时画面，有告警、有事件库、有统计。

"提出新网络结构"不在目标里。我们要做的是把成熟模型用对场景，并且能说清它在哪儿不行。

### 2.2 模型：只训"头"，两类

选 YOLO11 的理由很实际：Ultralytics 把训练、验证、导出、跟踪都包好了，`s` 规模在消费级显卡上能训能跑，社区资料够多。我们不需要自己发明网络，需要的是把现成的东西调到能用。

类别只设 `head`（没戴）和 `helmet`（戴了），一颗头只允许一个框。这样**框的数量就是头的数量，框的类别就是判定结果**，业务层不需要再判断"头盔框有没有落在头上"。

为什么不再训 `person`：

- 我们自己的 person 标注漏标多，这点噪声会带坏 head/helmet；
- 现成的 COCO 权重召回更高（下一节有数），还一张图都不用标。

模型规模用 `yolo11s`。早期只有一百多张自有图，换 m/l 只会更过拟合——实验记录里已经把"换 yolo11m/l、加注意力、把轮数堆到 200"列为不要做的事。真要上边缘设备，再试 `yolo11n` + ONNX。

数据以 SHWD 的工地部分为主：2,274 张 train / 282 val / 662 test，共 9,045 个 helmet、1,453 个 head。自采的 150 张（105 训练 / 45 验证）是唯一自己拍的数据，45 张 val 单独作为一条评测线；后面还要再标一批裸头补进去。SHWD 里那 11 万个"教室人头"框不要——它教模型把室内人脸当工地裸头，是另一个任务。

当前基线（`train4`，SHWD 官方划分，640 输入，50 轮）：

| 指标 | val | test |
|---|---:|---:|
| mAP50 | 0.82 | 0.81 |
| head AP50 | 0.68 | 0.68 |
| helmet AP50 | 0.96 | 0.94 |
| 误合规率 | 7.3% | 7.7% |

来源：[评测记录](评测记录.md)。三个读法：

- helmet 够用了，短板全在 head；
- 真正要盯的不是 mAP，是**误合规率**（真值是裸头、被判成 helmet 的比例）。把没戴的判成戴了，是安全场景里最不能接受的错误方向；
- 同一版模型在 val 上把 89/151 个裸头判成违规（58.9%）：11 个被判成"戴了"，18 个卡在阈值以下，5 个框偏了，28 个根本没检出。漏检集中在夜间、逆光和小目标上，进一步拆解见[E3 错误分解](E3错误分解.md)。这决定了产品必须配合人工巡查，对外不能说"全覆盖"。

顺带提醒：7.3% 这个数换个评测集就变（自有 45 张上，v3 是 3/10）。这类比例必须连着评测集一起说，不能单独摘出来当卖点。

### 2.3 匹配：COCO 管"人在哪"，规则管"头是谁的"

"用 COCO 做人-头盔匹配"这句话，落到代码里其实是两件事，别混：

1. 用 COCO 预训练的 `yolo11s.pt`（`classes=[0]`，只取 person）出人的框，**不训练**；
2. 用一条几何规则，把每个头框挂到某个人身上。

COCO 给的是"认得人"这个能力，不是匹配算法。匹配那十几行是我们自己写的。

```text
视频帧
  ├─ A 路  yolo11s.pt（COCO）      → person 框 + ByteTrack 的 track_id
  └─ B 路  best.pt（head / helmet） → 每颗头一个框
                 │
                 ▼
        归属：头框中心落在哪个人的"头部区域"
                 │
                 ▼
        单帧状态 → 按 track_id 连续帧投票 → 告警 / 抓拍 / 入库
```

为什么值得这么拆：同一批 45 张自有 val、147 个人工 person 框，960 输入、conf 0.40 下，COCO 权重召回 0.871 / 精确率 0.853；自训三分类里的 person 是 0.748 / 0.833。同一阈值下差 12 个召回点，代价是零张标注图。

归属规则，按顺序：

1. 取 person 框**上部 35%** 当"头部区域"；
2. 头框中心落在谁的头部区域里就归谁；多人重叠时取中心距离最近的；
3. 谁都不落 → **独立头**：照样判定、照样抓拍，但没有 track_id，不进连续帧投票。

判定只出三种结果：合规（helmet）、违规（head）、不确定（没有框）。不确定不告警，但要留记录。**最忌讳把"不确定"悄悄算成"合规"**——那等于系统替人做了它没把握的判断。

连续帧投票的初始值：15 帧滑窗、违规比例 ≥60%、轨迹不足 10 帧不判、同一 track_id 30 秒冷却。这些都要在现场视频上标定，别当最优参数写死。

代价也说清楚：

- 两路推理，960 输入在 5060 笔记本上实测约 17 fps，跑一路 25 fps 视频会掉帧。所以采集端要抽帧（5—10 fps）或降到 640；多路并发没压测过，答辩时别承诺能接几路。
- COCO 对远处小目标弱，人没框住时头会变成"独立头"——判定还在，跟踪和抓拍降级。
- 人群密集时可能挂错人。原则是"宁可漏，不可错"：拿不准的帧不计票。

### 2.4 什么算成功

不是"mAP 多高"，而是三条能当着老师面演出来的：

1. 给一段没参与训练的现场视频，系统能报出违规，截图能看清是谁；
2. 误报能人工标掉，且标掉的图能回收到难例集；
3. 从打开网页到导出本周违规记录，不超过 5 分钟，不用看说明书。

## 3 最终成品：Web 管理终端

最终交付形态是**一个网站**，不是脚本、也不是要装客户端的桌面程序：管理层用浏览器打开、登录，就能看到摄像头画面和告警。它跑在工地局域网里的一台机器上，摄像头由这台机器去拉，浏览器只看结果。

### 3.1 谁在用

设想一个早上：安全员在办公室打开浏览器，左边是几个摄像头的小窗，其中一路闪了红框——3 号楼二层有人没戴帽子；右边告警卡片带着截图、时间、摄像头名；点"已处理"，卡片消失。月底项目经理打开统计页，看到"本月违规集中在上午 9—11 点，2 号摄像头最多"，导出表格交上去。

管理层要的不是召回率，是"哪块地方、什么时候、处理了没有、有没有留痕"。页面就按这个排。

### 3.2 四个页面

| 页面 | 给谁 | 关键内容 | 第一版 |
|---|---|---|---|
| 实时监控 | 安全员 | 多路画面 + 检测框 + 在线状态 + 当前告警 | 要 |
| 事件中心 | 安全员 / 项目经理 | 按时间、摄像头、状态筛选；看抓拍大图；标"确认 / 误报" | 要 |
| 统计分析 | 项目经理 | 按日、摄像头、小时的违规趋势；导出 CSV | 要，可以很简单 |
| 系统设置 | 管理员 | 摄像头增删改、阈值、模型版本、单账号密码 | 要 |

"标误报"这个按钮很便宜但很有用：误报截图自动进 `hard_examples/`，下一轮补数据就从这儿挑。误报率能靠它一点点降下来，比反复调阈值靠谱。

### 3.3 摄像头怎么接

现场基本是 RTSP 网络枪机（海康、大华），地址形如 `rtsp://user:pass@ip:554/...`。浏览器不能直接播 RTSP，所以要后端拉流、转成浏览器能显示的东西。

| 方案 | 延迟 | 实现难度 | 适合 |
|---|---|---|---|
| MJPEG（后端出 JPEG，`<img>` 直接显示） | 低 | 最低，一两天能跑通 | 起步、演示、1—2 路 |
| WebSocket 推 JPEG 帧，前端 canvas 画 | 低 | 中，但框可以画在前端 | 想让画面和框分开刷新 |
| HLS（FFmpeg 切片） | 高（秒级） | 中 | 只想"看"，不要求及时 |
| WebRTC | 最低 | 高（信令、aiortc） | 以后再说 |

起步建议：后端拉流 → 抽帧 → 两路推理 → 把框画在图上 → JPEG → MJPEG。代码最少，答辩最不容易翻车。页面稳定后再考虑把"视频"和"框"拆开，让画面更顺。

必须处理的细节：断流自动重连（工地网络会抖）、用子码流（主码流太占带宽）、一路挂掉不能拖垮其他路、先只开 1—2 路。

### 3.4 技术栈（暂定）

| 层 | 选型 | 理由 |
|---|---|---|
| 推理 | Ultralytics YOLO11 + PyTorch | 已经跑通，别换 |
| 视频 | OpenCV + FFmpeg | RTSP 拉流最省事 |
| 后端 | FastAPI + Uvicorn | 轻、自带接口文档；团队熟 Flask 就用 Flask |
| 数据库 | SQLite | 零配置、单文件、好备份 |
| 前端 | Vue 3 + Vite + Element Plus | 表格、弹窗、布局都是现成的 |
| 图表 | ECharts | 中文资料多 |
| 推送 | WebSocket 或 SSE | 告警卡片能即时出现 |
| 部署 | 一台机器 + 局域网 | 现场断网也能跑 |

明确不引入：Redis、Celery、K8s、微服务、Docker 编排。这个规模用不上，学它们的时间够把判定逻辑调三遍。前端人手不够时，第一版直接用 FastAPI 模板页 + 少量原生 JS，接口定好，后面换 Vue 不用动后端。

### 3.5 一次告警要经过哪些环节

1. 拉流进程按 5—10 fps 取帧（不追 25 fps，追了也跑不满）；
2. 同一帧跑两路：person（带跟踪）和 head/helmet；
3. 头框按 2.3 的规则挂到人；
4. 按 track_id 记一票，滑窗够了才判违规；
5. 冷却期内不重复报；
6. 写事件：时间、摄像头、track_id、状态、置信度、截图（裁整个人，不是一颗头）；
7. WebSocket 推给页面，卡片出现；
8. 安全员点"已处理 / 误报"，状态回写。

任何一环断了，页面上的表现都是"没有新告警"。所以每环都要有日志，演示前重点看摄像头掉线、模型报错、数据库锁住这三种情况页面会是什么样。

### 3.6 演示兜底

答辩现场不能假设有工地摄像头、有网、有显卡。至少准备三手：本地视频回放（同一套 pipeline，输入换成文件）、USB 摄像头、提前录好的完整操作录屏加预置事件数据。

真到现场，能稳定跑本地视频，也比"连不上摄像头"强得多。

## 4 边界

**不做**：人脸识别、身份/工号、考勤、其他劳保用品（反光背心、安全带）、危险行为识别、跨摄像头重识别、云端多租户、手机 App。

**不承诺**：夜间、强逆光、远距离小目标、严重遮挡下的稳定识别。系统是"辅助提醒"，不替代现场安全管理。

**合规**：拍摄前取得管理方许可；对外素材人脸打码；现场视频不外传；Ultralytics 是 AGPL-3.0，竞赛演示没问题，将来要商业化得单独评估。

## 5 分阶段

| 阶段 | 目标 | 完成标志 | 粗排期 |
|---|---|---|---|
| M0 离线闭环 | 图片/视频进，事件表和截图出 | 一条命令跑完一段视频，出 CSV + 截图 | 约 1 周 |
| M1 单路实时 | 一路 RTSP / USB，浏览器看到带框画面 | 页面刷新能看到框，延迟可接受 | 约 1 周 |
| M2 管理终端 | 多路 + 事件中心 + 统计 + 设置 | 演示脚本能从打开页面走到导出 | 约 2 周 |
| M3 打磨 | 断流重连、长时间运行、现场视频回归 | 连续跑 2 小时不崩，误报有记录 | 1—2 周 |

排期是按 4—5 人、课余时间拍的，不是承诺。人少就砍 M2 的多路和统计，先把 M0—M1 做扎实。

M0 值得单独说一句：**先不碰网页**。判定逻辑对不对，用一段视频和一张 CSV 就能看出来；套上界面再调逻辑，效率会低很多。

## 6 还没定的事

| 问题 | 为什么现在就要问 |
|---|---|
| 现场能不能给 RTSP 地址和账号（还是只能给 NVR） | 决定"实时"是真能演示，还是只能放录像 |
| 摄像头装多高、拍多远、有没有逆光 | 决定要不要 960、要不要切片，也决定指标怎么报 |
| 演示机器有没有独显、现场有没有网 | 决定兜底方案和帧率 |
| 误合规那部分怎么处置 | 要不要"待复核"队列，谁来看 |
| 前端谁写、每周能投多少时间 | 决定第一版是 Vue 还是模板页 |
| 权重和数据集能不能公开 | 影响仓库、答辩材料和许可证说明 |
